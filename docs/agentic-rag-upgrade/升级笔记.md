# 知枢星图 · Agentic RAG 升级笔记

> 本笔记记录知枢星图从「基础 RAG」升级到「Agentic RAG」的完整过程：架构决策、踩坑记录、价值沉淀。
> **维护规则**：有进展就往下追加。新坑 →「四、踩坑记录」；新决策 →「三、架构决策」；新进展 →「六、进展日志」。

## 一、升级概述

| 项 | 内容 |
|---|---|
| 升级主题 | 基础 RAG → Agentic RAG（LangGraph + 完整三查反思） |
| 一句话目标 | 让 AI 从"搜一次就答"升级为"自主决定搜什么、自查答案质量"的 Agent |
| 设计文档 | `docs/superpowers/specs/2026-08-03-agentic-rag-upgrade-design.md`（v0.2） |
| 完成状态 | M0-M5 主体已完成；收尾遗留统一记录在 `待做清单.md`（联网意图缺陷、Tavily key、Langfuse trace 上报等） |

**为什么值得做**：现有 RAG 是"一次性检索 → 喂给 LLM → 出答案"的单程流水线，缺 7 样东西：无查询改写、无工具调用、无迭代检索、无自我反思、无路由、知识图谱是孤岛、无可观测性。升级后这些全补齐。

## 三、架构决策（为什么选这个）

> 每条都是经架构评审 + 逐点讨论敲定的，附「为什么」和「备选为什么不选」。

### D1. 框架选纯 LangGraph，不叠加 Pydantic AI、不手写循环
- **为什么**：现有项目锁定 `langchain-core<1.0.0`，LangGraph 0.2.x 与其兼容；checkpoint / HITL interrupt / 流式全原生；官方 agentic-rag 教程参考实现最多，面试讲"图状态机 + 条件边"最站得住。
- **备选为什么不选**：Pydantic AI 是另一套 agent 框架，叠加进来要写大量胶水代码；"手写 ReAct 循环"等于放弃 LangGraph 的核心价值（图编排、持久化），且 Pydantic AI 自带循环，没必要手写。

### D2. 反思做成「三个强制节点」，不是「工具」
- **为什么**：反思靠 LLM 自觉调用会失效（模型很懒）。做成图节点 + 条件边，由结构强制保证"每一步都检查"，LLM 只负责判断、不负责"要不要检查"。符合 LangChain 官方 Self-RAG 标准。
- **三查**：① `grade_documents`（搜到的资料相关吗，不相关改写重搜）→ ② `hallucination_check`（答案有出处吗，没出处重写）→ ③ `answer_quality`（答到点了吗，跑题重搜重答）。

### D3. 推理模型用 deepseek-v4-flash + 显式关思考模式
- **为什么**：`deepseek-chat`/`deepseek-reasoner` 已于 2026-07-24 **退役**；V4 默认思考模式会拒绝强制工具调用（HTTP 400），关掉思考后工具调用全兼容、还快 2.6 倍、更省 token。
- **备选为什么不选**：V4 思考模式虽然也能调工具，但必须把 `reasoning_content` 完整回传后续请求（极易出错 400）、慢、且强制工具仍 400，复杂度高不值当。

### D4. Embedding 换 qwen3.7-text-embedding，新增前置 M0 全库重索引
- **为什么**：`text-embedding-v3` 已下线（不可用），必须换。换 embedding 模型 = 向量空间不兼容 = 全库重向量化 + 重建 FAISS 索引，所以 M0 是硬前置，不做 M1 的检索就是空的。

### D5. 评估裁判用 qwen3.8-max 独立裁判，不引 RAGAS
- **为什么**：避免"生成模型自己给自己打分"的同源偏差；RAGAS 对中文 + 非 OpenAI 模型兼容性差；DashScope key 现成，自实现可控。
- **指标构成**：recall@k 纯计算（确定性，最可靠）+ faithfulness / answer_relevancy 用独立裁判 + 抽 10 条人工校准。

### D6. 工具层用 LangChain `@tool` + Pydantic，不用 Pydantic AI
- **为什么**：框架已定 LangGraph，同一生态，避免引入第二套 agent 框架。

### D7. 记忆：短期 checkpoint + 长期 store（+ user_preferences 表），旧模块退役
- **为什么**：这是 LangGraph 官方标准的记忆模型（checkpoint 管线程内、store 管跨线程）。旧的 FAISS 记忆模块与它重复，退役避免两套向量体系并存。偏好信息单独建表（用户拍板），便于管理。

### D8. MCP：API Key 认证 + 挂进现有 FastAPI
- **为什么**：MCP 的 Streamable HTTP 协议不内置认证，不加门禁外部程序能裸读私密笔记；API Key 对个人场景最务实。挂 FastAPI 配置极简，本地调用量小，不用另起进程。

### D9. HITL 用双通道标准版（SSE 流式 + interrupt + POST resume）
- **为什么**：LangGraph 官方 + GitHub 成熟模板的标准做法——流式走 SSE、审批走 POST，用同一个 `thread_id` 串起来，不把审批塞进流里。

### D10. 可观测用 Langfuse 云版
- **为什么**：给 AI 装"行车记录仪"（每次推理过程、工具调用、token 成本全记录），快速跑通不占本地资源。自建 Docker 作为后续加分项。

### D11. 防注入用基本隔离（数据边界包裹）
- **为什么**：导入的网页/PDF 笔记可能藏"忽略指令"的坏话，用不可信数据边界 + system prompt 声明隔开。个人场景够用。

### D12. M5 采用 Langfuse 优先 + 本地审计自动降级
- **为什么**：M2 已确认 Langfuse SDK/OTel 组合存在环境不确定性；可观测面板不能因云端 Key、网络或 SDK 故障变成空白页。
- **实现**：配置有效时从 Langfuse Trace API 读取 latency/token/cost；未配置或请求失败时自动用 `agent_sessions` + `agent_tool_calls` 生成 trace 列表、成功率、延迟和工具分布，并明确显示数据源/降级原因。
- **收益**：云端能力恢复后无需改前端；离线环境仍有完整的工具审计与 HITL 状态可见性。

## 四、踩坑记录（碰到的坑）

> 这些坑都是本次评审/调研中真实踩到或预见到的，每个都值得面试讲。

### P1. `deepseek-chat` 已退役，v0.1 设计里的模型名是死代码
- **现象**：原设计写 `deepseek-chat`，查证发现该模型名 2026-07-24 已彻底不可用（截至 2026-08-06）。
- **根因**：DeepSeek 从 V3 升级到 V4，旧别名退役，新模型只有 `deepseek-v4-flash` / `deepseek-v4-pro`。
- **规避**：用 `deepseek-v4-flash` + `extra_body={"thinking":{"type":"disabled"}}`，行为等价于旧 `deepseek-chat`。

### P2. DeepSeek V4 思考模式拒绝强制工具调用（HTTP 400）
- **现象**：V4 默认思考模式，`tool_choice="required"` 或指定函数会直接 400。
- **根因**：思考模型"不愿在思考前承诺用哪个工具"，官方限制。
- **规避**：显式关思考模式。这直接影响三查节点（`with_structured_output` 依赖强制工具）。
- **教训**：选模型前先查它的 function calling 契约，别只看"能用"。

### P3. langgraph 版本冲突：1.x 需要 langchain-core≥1.0，与现有锁定的 <1.0.0 冲突
- **现象**：`pip install langgraph` 若装到 1.x，会和现有 `langchain-core<1.0.0` 解依赖失败。
- **规避**：锁 `langgraph>=0.2.50,<0.3.0`。
- **教训**：给快速迭代的框架写 `>=` 裸约束 = 埋雷，必须锁大版本。

### P4. embedding v3 下线 → 全库重索引不可避免
- **现象**：`text-embedding-v3` 不可用，必须换模型。
- **根因**：不同 embedding 模型向量空间不兼容，旧向量不能和新向量混用。
- **规避**：新增 M0 前置任务，写 re-index 脚本全库重建。先验证新模型维度（现有代码硬编码 1024）。

### P5. 反思做成「工具」会导致闭环失效（设计层面的坑）
- **现象**：v0.1 把 `grade_answer`/`check_grounded` 做成工具让 LLM 自主调用，被评审指出"LLM 不会自觉检查，反思会形同虚设"。
- **规避**：改成强制图节点 + 条件边。
- **教训**：涉及"质量保障"的环节，别依赖模型的自觉，用结构保证。

### P6. RAGAS 对中文 + 非 OpenAI 模型兼容性差
- **现象**：RAGAS 是现成评估工具，但对 DeepSeek / 中文支持不稳定。
- **规避**：自实现 judge（纯计算 recall + 独立裁判模型）。
- **教训**：热门工具不一定适配你的模型和语言，先验证再引。

### P7. MCP 无认证 = 私密笔记裸奔
- **现象**：设计 v0.1 的 MCP 配置只有 url，没有任何鉴权。
- **根因**：Streamable HTTP 协议不内置认证。
- **规避**：API Key 中间件。

### P8. token 预算 4000 过紧
- **现象**：多跳推理 + 三查 + 历史，4000 token 跑不完一轮。
- **规避**：提到 10000，且给工具返回设上限（`get_note` 前 2000 字、snippet ≤300）。

### P9. 依赖版本裸约束的普遍坑（pydantic-ai 0.0.x vs 2.x）
- **现象**：设计写 `pydantic-ai>=0.0.30`，实际已 2.x，API 完全不同。
- **规避**：写版本前查最新版本，锁大版本。
- **教训**：2026 年的 agent 框架迭代极快，版本号必须核实。

### P10. 现有 rebuild_index.py 写入的 store 与 search 实际读取的不一致
- **现象**：`scripts/rebuild_index.py` 走 `get_vector_store_adapter()` 写入；当 `.env` 开了 `USE_LANGCHAIN_VECTORSTORE=true` 时它写的是 LangChain store，而 `hybrid_search._vector_search` / `vector_search_notes` 实际读的是原生 `get_vector_store()`。且原生 store 若存 chunk_id（`{note_id}_chunk_{i}`），`db.query(Note).filter(Note.id==chunk_id)` 解析不到笔记 → 向量侧静默失效。
- **规避**：M0-4 重写 `reindex_all.py`：直接写原生 store、每笔记一个向量、key 用真实 note.id（块向量均值池化），从根上规避适配器双后端与 chunk_id 解析问题。
- **教训**：双后端（原生/LangChain）+ 统一适配器是技术债；写入前先确认读侧真正读哪个 store、返回的 id 能否反查笔记。

### P11. 用户 site-packages 的 pydantic_core 损坏 + 服务的 sys.path hack 会静默劫持
- **现象**：`embedding_service.py` / `vector_store.py` 里 `sys.path.insert(0, user_site)` 兼容 hack，把用户 site 提到最前；用户 site 的 pydantic_core 是多版本残留损坏（`__init__.py` 期望的 `validate_core_schema` 不在编译 .pyd 里）。单独 import 这些模块 → ImportError。
- **规避**：app 本身不受影响（`app.main` 先 import fastapi，把 Anaconda 健康 pydantic 2.10.3 + pydantic_core 2.27.1 缓存进 sys.modules）；**独立脚本必须先 `import app.core.config` 再 import 服务模块**，避免 hack 先跑。
- **教训**：环境 hack 是隐形雷，脚本/服务的导入顺序会影响包解析。

### P12. 旧对话记忆索引绑定已下线 embedding 模型
- **现象**：`chat_memory_store.py` 的 LangChain FAISS 索引向量来自旧模型；新模型维度虽同为 1024，但语义空间不兼容，召回会是垃圾。
- **规避**：M0 先 `.env` 置 `USE_VECTOR_MEMORY=false`；完整退役放 M4（LangGraph checkpoint + store 取代）。

### P13. DeepSeek V4 官方通道不支持 response_format(JSON mode)
- **现象**：`llm.with_structured_output(Model)` 默认走 `response_format`，DeepSeek 官方通道直接 400 `This response_format type is unavailable now`。
- **规避**：`with_structured_output(Model, method="function_calling")`——底层是强制 `tool_choice` 指定 schema 函数，不走 response_format，实测可用（`verify_deepseek_tools.py` 4/4 通过）。
- **教训**：三查节点依赖结构化输出，务必统一走 function_calling 方法；已在 `DeepSeekProvider.with_structured_output` 里 `setdefault("method", "function_calling")`。

### P14. langgraph-checkpoint-sqlite 安装会顺带升级 langgraph-checkpoint 到 4.x，与 langgraph 0.2.x 冲突
- **现象**：`uv pip install langgraph-checkpoint-sqlite`（最新 3.x）把 `langgraph-checkpoint` 从 2.1.2 升到 4.1.1（那是给 langgraph 1.x 的），`langgraph` 直接报错（`module 'langgraph' has no attribute '__version__'`）。
- **规避**：锁版本 `langgraph-checkpoint==2.1.2` + `langgraph-checkpoint-sqlite>=2,<3`（2.0.11 与 checkpoint 2.x 配套）。
- **教训**：langgraph 生态拆成多个包后，装可选扩展必须同步锁主包版本（P3 的延伸）。

### P15. 用 Git Bash 的 curl 发中文 query 会按 GBK 编码，服务器按 UTF-8 解成乱码 → 检索空
- **现象**：Windows Git Bash 终端 locale 是 GBK，`curl --data-urlencode "q=科技"` 发出去的字节是 GBK，服务器按 UTF-8 解码成乱码，检索全空。初看像"服务器检索坏了"。
- **规避**：验证检索/SSE 用 `python requests`（显式 UTF-8）或 URL 里用 UTF-8 百分号编码；别用 Git Bash 的 curl 发中文。另外服务器 cwd 不一致会导致相对路径 `DATABASE_URL` 指向不同 DB → 旧 token 失效，误判为 401/空结果。
- **教训**：跨平台 CLI 测试中文参数要先确认编码；排查"检索空"先排除编码/认证假象再怀疑代码。

### P16. qwen3.8-max 默认 thinking mode 拒绝强制 tool_choice（HTTP 400）
- **现象**：M2-3 验证裁判时，`with_structured_output(method="function_calling")` 直接 400 `tool_choice does not support required/object in thinking mode`，与 DeepSeek V4 的 P2 一模一样。
- **规避**：ChatOpenAI 构造加 `extra_body={"enable_thinking": False}`（qwen3.8-max 关思考开关，注意不是 DeepSeek 的 `thinking:disabled`），关后结构化输出 2/2 通过。
- **教训**：裁判模型默认开 thinking，评估这类"强制工具调用"场景必须显式关思考；不同厂商关闭思考的参数名不同（DeepSeek `thinking:disabled` vs Qwen `enable_thinking:false`）。

### P17. langfuse 版本与集成路径的连环坑（2.x / 3.x / 4.x 各有坑，M2-6 标记环境遗留）
- **现象**：接入 langfuse 尝试多个版本均受阻——**2.x** 的 langchain 集成用老路径 `langchain.schema.agent`，与项目锁定的 langchain 0.3.x 不兼容（报 "Please install langchain"）；**3.x/4.x** 改走 OpenTelemetry，运行时崩 `TraceFlags has no attribute 'RANDOM_TRACE_ID'`。
- **规避（环境层，已验证）**：`RANDOM_TRACE_ID` 崩溃的根因之一是 `--system-site-packages` 混入 Anaconda 旧版 opentelemetry（namespace 混搭）。**新建干净 `.venv`（uv venv 不带 --system-site-packages）后** `opentelemetry.trace.TraceFlags` 单独测正常。`requirements.txt` 相应补了 `langgraph-checkpoint==2.1.2`（M1 遗漏）+ `importlib-metadata`（Python 3.13 移除标准库）。
- **仍未解决**：干净环境下 langfuse 4.x 运行时 `on_chain_start` 仍崩 `RANDOM_TRACE_ID`，但单独模拟 `TraceFlags(SAMPLED | RANDOM_TRACE_ID)` 却正常——疑似 langfuse 4.x 与 opentelemetry-sdk 1.44.0 深层不兼容。**M2-6 标记环境遗留**；评测用显式禁用 langfuse（env 置空 key）跑，fail-silent 保证不影响主流程。
- **教训**：接入第三方可观测 SDK 前先验证其与当前 langchain/otel 版本组合的**真实运行**（非仅 handler 初始化成功）；`--system-site-packages` 的 namespace 混搭是隐形雷，排查"某包诡异报错"先查 sys.path 混入源。

### P18. 评测 faithfulness 误判：agent 证据用 snippet 导致几乎全 0
- **现象**：M2-4 首轮全量报告 agent faithfulness 0.045（baseline 0.947），而 answer_relevancy 正常——几乎全判"答案无出处"。
- **根因**：agent 的 `search_notes` 工具返回 snippet ≤300 字，评测把 documents(snippet) 当裁判证据；裁判因证据信息不足判"不 grounded"。实测同一答案用完整笔记内容当证据：**0.0 → 1.0**。
- **规避**：`run_eval.py` 增加 `get_full_sources`（按检索 ids 从 DB 取 ≤2000 字完整内容）作为 agent faithfulness 裁判证据，与 baseline 公平对齐。修复后 agent faithfulness 0.891（合理）。
- **教训**：评估 faithfulness 的证据口径必须覆盖模型真实可访问的信息（agent 可经 get_note 取全文），只给截断片段会系统性误判。

### P19. 设计文档的 fastmcp 0.x 版本预估已过时，实际是 3.x 且 API 断代
- **现象**：设计文档写 `fastmcp>=0.4.0,<1.0.0`，实际装到 **3.4.7**；且 3.x 与旧版 API 差异大——`mount_to_fastapi` 不存在；`Client()` 不接受 `headers` 参数（须 `Client(StreamableHttpTransport(url=..., headers=...))`）。
- **规避**：锁 `fastmcp>=3,<4`；写集成代码前先 `inspect.signature` 探测实际 API 再动手。
- **教训**：agent 生态框架迭代极快（P9 的延续），设计文档里的版本号只是编写时的快照，实施时必须重新核实。

### P20. uv 安装 fastmcp 引发 langchain-openai 包目录缺失 + user-site langchain 1.x 劫持
- **现象**：装完 fastmcp 后 `import app.main` 炸 `cannot import name 'ContextOverflowError' from 'langchain_core.exceptions'`——`langchain_openai` 从 Anaconda 加载 1.1.11（需要 1.x 符号），`langchain_core` 却是 `.venv` 的 0.3.86，两者错配。
- **根因**：`.venv` 里 langchain-openai 只有 dist-info 记录、import 找不到包本体，静默回退到 Anaconda 的 1.1.11；`embedding_service.py` / `vector_store.py` 顶部的 `sys.path.insert(0, user_site)` hack（P11）还会把 user site 的 langchain 1.x 全家桶插到 sys.path 最前，进一步劫持包解析。
- **规避**：`uv pip install --reinstall langchain-openai==0.3.35` 补齐 `.venv` 包目录（与 langchain-core 0.3.86 配套）；**根除两个服务文件的 sys.path user-site hack**（启动文档早已声明不再需要）。
- **教训**：`--system-site-packages` venv 里"某包有 dist-info 但 import 不到包本体"会静默 fallback 到 system site 的不同大版本；user-site hack 一日不除，劫持风险一日存在。

### P21. StreamingResponse 线程池切换导致 ContextVar Token 跨上下文复位失败
- **现象**：真实 HTTP 冒烟时 SSE 已返回 200，但响应末尾提前断开；服务端报 `ValueError: Token was created in a different Context`。
- **根因**：Starlette 会在 worker thread/context 中分段调用同步 generator 的 `next()`；在 generator 首次迭代创建的 ContextVar token，不能保证在 finally 所在的 context 中 reset。
- **规避**：把 ToolContext 的 set/reset 下沉到 `execute_tool` 节点内，确保工具调用与复位发生在同一个同步执行上下文；流生成器不再持有跨 `yield` 的 ContextVar token。
- **验证**：真实认证 HTTP 链路重新跑通，SSE 正常包含 `final_answer` 与 `[DONE]`，日志无 ASGI 异常。

## 五、价值沉淀（简历 / 面试可用点）

### 5.1 技术亮点（简历词）
- **Agent 框架**：基于 LangGraph 构建 ReAct 推理循环（Thought-Action-Observation），实现 LLM 自主调度检索/图谱/反思工具。
- **反思能力**：集成 Self-RAG 三查反思（资料相关性 / 答案 grounding / 回答有用性）作为图节点强制路由，保证答案质量。
- **工具生态**：检索、图谱、笔记 CRUD、Web 搜索统一为类型化工具（Pydantic schema）。
- **MCP 化**：将知识库封装为 MCP Server（API Key 认证 + 挂载 FastAPI），支持 Claude Desktop / Cursor 直接检索。
- **记忆分层**：短期 checkpoint + 长期 store 双层记忆（LangGraph 官方标准）。
- **可观测性**：接入 Langfuse 实现全链路 trace，覆盖每次工具调用与推理。
- **评估体系**：构建 50 条评测集，recall@k 纯计算 + 独立裁判 + 人工校准，量化升级效果。

### 5.2 可量化的点（M2 全量评测已回填，2026-08-17）
- 50 条评测集新旧对比：recall@k **0.993（baseline）/ 0.983（agent）**，faithfulness **0.962 / 0.891**，answer_relevancy **1.000 / 0.936**——agent 与 baseline 基本持平；agent 在简单题（q017/q018/q025）上发挥不稳定，是可优化点。
- 人工校准一致率：faithfulness 9/10（90%）、answer_relevancy 10/10（100%），裁判可信。
- 三查通过率 / 工具调用次数 / 单次推理成本（Langfuse 统计）：待 trace 上报修复后补充（见 `待做清单.md` TODO-4/7）。

### 5.3 面试技术深度问答预演
- **为什么选 LangGraph 不选 Pydantic AI / 手写循环？**
  → 答：现有生态是 langchain；LangGraph 原生提供 checkpoint/HITL/流式/条件边，反思强制节点正是图的强项；Pydantic AI 更适合单 agent 请求响应，两者叠加重。
- **反思为什么是节点不是工具？**
  → 答：工具由 LLM 自觉触发，实测会偷懒失效；图节点 + 条件边由结构强制保证每轮都检查，LLM 只做判断不做"要不要检查"的决策。
- **DeepSeek 有什么坑？怎么处理的？**
  → 答：deepseek-chat 已退役；V4 默认思考模式拒绝强制 tool_choice（400）；解决是显式 `thinking:disabled`，工具调用全兼容且更快更省。
- **为什么换 embedding 模型？代价是什么？**
  → 答：v3 下线必须换；换模型向量空间不兼容 → 全库重索引（M0），所以 embedding 选型要谨慎、要评估重索引成本。
- **MCP 为什么要加认证？**
  → 答：Streamable HTTP 不内置认证，知识库是私密数据，必须 API Key 门禁。
- **评估怎么做？为什么不用 RAGAS？**
  → 答：RAGAS 对中文/非 OpenAI 兼容差；用确定性 recall + 独立裁判模型 + 人工校准，避免同源偏差。

### 2026-08-28 —— M6 完成：意图识别（Intent Routing）四分类路由

- **背景**：M2 评估发现 agent 在简单题（单轮检索就够）上反而掉链、不如 baseline——所有问题都跑完整 ReAct + 三查，浪费 token 且不稳定；同时 TODO-1 记录"联网搜索意图被误拒"缺陷。两者统一解法：图入口加 LLM 意图分类路由。
- **方案来源**（GitHub 调研）：业界 agentic RAG 统一模式 =「结构化分类节点 + 条件边路由」。参考 LangChain 官方 router-knowledge-base、JEONGHEESIK/LangGraph-Agentic-Graph-RAG（knowledge/calculation/database/api_call/code_exec）、sotaaz Query Routing（requires_retrieval 跳过检索）。
- **实现**：
  - `prompts.py`：`QueryIntent`（Pydantic + Literal 四分类）+ `INTENT_CLASSIFY_PROMPT` + `DIRECT_ANSWER_PROMPT` + `INTENT_HINTS`（web_search / note_write 意图提示）。
  - `nodes.py`：`intent_classify`（结构化输出，**fail-safe 默认 knowledge**，失败不阻塞）、`direct_answer`（短路直答，跳过工具/三查，写 checkpoint 保多轮上下文）、`route_intent`（条件边）；`agent_step` 首轮注入意图提示。
  - `graph.py`：`START → intent_classify →(条件边)→ agent_step | direct_answer → output`。
  - **四类意图**：`knowledge`（知识库检索 → 现有 ReAct+三查）/ `direct_answer`（常识闲聊 → 短路直答，省 token 修简单题回归）/ `web_search`（实时/明确联网 → ReAct + web 提示）/ `note_write`（写入 → ReAct + create_note 提示，复用 HITL）。
  - **eval**：`run_eval.py` 采集意图分布 + 平均工具调用数，报告新增「Agent 意图分布与成本」段。
  - **前端**：时间线新增「意图识别」节点（Compass 图标 + 紫色）。
- **顺带修复 TODO-1（联网搜索意图误拒）**：① `REACT_SYSTEM_PROMPT` 新增 web_search 使用规则（不再拒答）；② `intent_classify` 显式识别"联网/上网搜索"；③ `execute_tool` web_search 成功结果并入 `documents` 证据池（供三查核对）；`GRADE_HALLUCINATIONS_PROMPT` 证据口径改为"本地笔记或联网搜索结果"。
- **新增熔断（防死循环）**：web_search 返回"永久未启用"（无 TAVILY_API_KEY）后，同线程后续 web_search 请求在 `execute_tool` 直接短路（确定性拦截，不再烧 token）。待做清单要求"不应死循环改写重搜"已闭环。
- **踩坑/修正**：初版意图提示词把带历史日期的知识库问题（"5月10日…"）误判成 web_search → 提示词加规则"事件带明确历史日期归 knowledge，只有明确当下/实时/联网才归 web_search"，修正后 eval 冒烟 2/2 归 knowledge、平均工具调用 2.0→1.0。
- **验证**：后端 **43 passed**（新增 7 用例：路由 2 + 分类 3 + 直答 1 + 熔断 1）；前端 `vue-tsc --noEmit` 0 错误；真实链路冒烟——闲聊→direct_answer 直答、多跳问题→knowledge 完整 ReAct、联网→web_search + 熔断降级、无 TAVILY key 时 web_search 明确报"未启用"不再死循环。

- **q014/q039 专项排查与修复（2026-08-29 后段）**：两条件 eval 双双 0.000，深挖执行日志定位三个病灶（均非意图路由问题，都正确归 knowledge）：
